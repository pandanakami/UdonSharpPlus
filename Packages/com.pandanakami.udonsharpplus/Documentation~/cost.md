# 負荷の目安

UdonSharp Plus の機能を使ったとき、書き換えたコードが、**実行するたびに** Udon で重いとされている処理（`new`、`SendCustomEvent`・`GetProgramVariable`・`SetProgramVariable`）をするかの一覧です。速度の計測ではありません。毎フレーム呼ぶところで使ってよいかを考える材料にしてください。

数えているもの：

- **Send**：`SendCustomEvent`
- **Get**：`GetProgramVariable`
- **Set**：`SetProgramVariable`
- **new**：GC の対象になるメモリを確保する命令。`object[]`（普通のクラス・タプル・匿名型・キャプチャ配列・デリゲート）、`DataList`・`DataDictionary`、そのほかの配列（`DataToken[]`・`int[]` など）、string の連結

キャプチャ配列は、ラムダが外側の変数を使うこと（キャプチャ）のために、その変数を入れる `object[]` です。`DataToken` は構造体なので、作っても確保にはなりません（数えていません）。

数え方：書き換え後の UASM（Udon のアセンブリ）で、操作を書いたメソッドの入口から、実行のときに通る命令（呼び出すメソッドの中も）をたどって数えました。初期化（フィールドの初期化子）や、`+=`／`-=` の補助メソッドのように、操作のたびには通らないところは数えていません。「グループごと」は、ループの中にあって、その回数だけくり返すものです。

「実際の確保」は、エディタのプレイモードで 1 回動かしたときの、GC の確保の回数とバイト数を測った目安です（VRChat のクライアントで測った値ではありません。要素やグループの数で変わるものがあります）。ボックス化（値の型を `object` として扱うときに、箱に入れること）のように、`new` の命令に現れない確保も入っています。

## UdonSharp で書いた場合との比べ

UdonSharp Plus の機能は、書き換えたあと、UdonSharp で書けるコードになります。各機能が UdonSharp で書くと何に当たるかの目安です。細かい数は、下の「一覧」にあります。

| 機能 | UdonSharp でいうと |
|---|---|
| 普通のクラスのメソッド呼び出し・フィールドを読む | 同じ UdonSharpBehaviour のメソッドの呼び出し・`object[]` の要素を読むのと同じ（軽い） |
| 普通のクラスの `new`、タプル・匿名型を作る | `new object[]` 1 つと、値の型のフィールドのボックス化 |
| インタフェース経由・デリゲートの呼び出し（相手が UdonSharpBehaviour） | **ほかの UdonSharpBehaviour の引数付きメソッドを 1 回呼ぶのと同じ**（相手が自分自身でも） |
| インタフェース経由の呼び出し（相手が普通のクラス） | 型を比べて、同じ UdonSharpBehaviour のメソッドを呼ぶのと同じ |
| ラムダを作る | `new object[]` 1 つ（外の変数をキャプチャするなら 3 つ） |
| List・Dictionary | `DataList`・`DataDictionary` を直接使うのと同じ（要素は `DataToken` で包むだけ） |
| LINQ・List のメソッドに直接書いたラムダ | 手で書いた `for` ループと同じ（`ToList()` なら、結果の `DataList` 1 つ） |
| `GroupBy` | 上に加えて、グループごとにキーのボックス化（グループをつなぎの外に出すときは、グループごとに `new object[]` と `new DataList()` も） |
| 演算子のオーバーロード・ジェネリックメソッド | 同じ UdonSharpBehaviour の static メソッドの呼び出しと同じ |
| UniTask の async / await | コルーチンと同じ（`async` のメソッドを、コルーチンに書き換えます。[UniTask](unitask.md)）。値を返す `UniTask<T>` は、呼ぶたびに戻り値の置き場の `object[]` を作り、確保が増えます。`WhenAny`・`DelayFrame` は、待っている間も 1 フレームごとに確保します（下の「UniTask の async / await」） |
| コルーチン | 次のフレームを待つものがあるビヘイビアごとに 1 フレーム 1 回、`WaitForSeconds` で待つたびに 1 回の、遅れのイベントの予約。状態は使い回すので、同時に動く数が増えたときだけ `object[]`（下の「コルーチン」） |

ほかの UdonSharpBehaviour のメソッドを呼ぶ重さについては、下の「ボックス化と、ほかの UdonSharpBehaviour とのやり取り」を見てください。

### 注

- ※1 普通のクラス・タプル・匿名型は、値の型（`int` など）のフィールドを、作るときと書くたびにボックス化します（値を `object[]` に入れる作りのため）。値の型のフィールドに書くと、1 回・20 B です。読むこと・メソッドを呼ぶことは、確保しません
- ※2 Get は、戻り値があるときだけです。確保は、値の型の引数・戻り値 1 つにつき 1 回です（測ったのは、引数なし・`int` を返すメソッド）
- ※3 Set は、ラムダがキャプチャしていると 1 つ増えます。確保は、引数と戻り値の受け渡しのボックス化です（下の「デリゲートの呼び出し」）。`+=` でつないだデリゲートは、Send・Get・Set をつないだメソッドごとにくり返しますが、確保は呼び出し 1 回あたり 5 回ほどです（下の「デリゲートの呼び出し」）
- ※4 配列は、要素数の大きさです（`ToArray()` は `int[]` など、`string.Join` は `string[]`）。`List.Sort` の作業用の配列（`DataToken[]` 2 個）は、呼び出し箇所ごとに使い回します。初めは 16 個分で、それより多い要素を並べ替えたときだけ、倍の大きさで作り直します。普通のクラスのメソッドの中（UdonSharp は static フィールドを使えないため）では、呼ぶたびに要素数の大きさで 2 個作ります（要素 10 個で 2 回・544 B）
- ※5 要素を 1 つずつ文字列にする分を含みます
- ※6 結果の List です。並べ替えなどの作業用の `DataList` は使い回すので、呼ぶたびには作りません。実際の確保には、結果の List が大きくなる分を含みます
- ※7 グループが 3 つのときです。確保は、値の型（`int` など）のキーのボックス化で、グループの数だけ増えます。グループの入れ物（`object[]` と要素の `DataList`）は、グループがつなぎの外に出ないとき（集計だけするとき）は、呼び出し箇所ごとに使い回します。グループを外に出すとき（`ToList()`・`First()`・`foreach` でグループを受け取る、ラムダの中でグループを変数に入れる・ほかのメソッドに渡す、など）と、普通のクラスのメソッドの中では、呼ぶたびにグループごとに作ります（グループが 3 つで 30 回・1268 B）
- ※8 演算子のメソッドが `new` するとき（`a + b` がクラスの値を新しく作るなど）は、その分（普通のクラスの `new` と同じ）が増えます
- ※9 `n` のボックス化を含みます

## 軽くしているところ

使う側が何もしなくても、次のところは軽くなるように書き換えています。LINQ やラムダを、必要以上にためらわなくて大丈夫です。

- **LINQ や List のメソッドに直接書いたラムダは、デリゲートにしません。** `Where(x => ...)`・`Select`・`Any`・`Count`・`First`・`List.ForEach`・`List.Exists` などに書いたラムダは、書き換えたメソッドの中のループに、そのまま埋め込みます。デリゲートの値も、`SendCustomEvent` も使いません。ブロックのラムダ（`{ ... return ...; }`）と、メソッド名を渡す形（`Where(IsBig)`）も同じです（Send・Get・Set は 0、確保も増えません）。
- **LINQ のラムダが変数をキャプチャしても、キャプチャ配列（`object[]`）は作りません。** キャプチャした変数は、書き換えたメソッドの引数（書き換えるものは `ref`）で受け取ります。デリゲートのラムダが変数をキャプチャすると `object[]` を 3 個作りますが、LINQ に書いたラムダなら 0 個です。
- **LINQ のつなぎは、1 つのループにまとめます。** `Where(...).Select(...).ToList()` は、メソッドごとに途中の List を作らず、結果の List 1 個（と DataToken）だけです。
- **値を 1 つにまとめる LINQ は、確保しません。** `Any`・`Count`・`First`・`Sum` は、List も DataToken も作りません（テストで確かめたもの）。
- **List の `foreach` は、列挙子を作りません。** 添字のループにします。タプルのリストを回すとき（`foreach (var (a, b) in list)` の分解も）も、要素を読むだけで、確保はありません（タプルは、作るときに `object[]` を 1 個作ります）。
- **`List.Sort` に直接書いたラムダも、デリゲートにしません。** 生成する並べ替え（安定なマージソート）の比較のところに埋め込むので、比較 1 回ごとの確保はありません（ラムダの本体が何かを作らなければ）。
- **インタフェース経由の呼び出しで、実装する普通のクラスが 4 個以上のときは、型番号の `switch`（ジャンプテーブル。番号から飛び先を直接引く表）で振り分けます。** 型名を 1 つずつ比べないので、クラスの数が増えても、呼び出しの重さは変わりません。
- **普通のクラスのメソッド呼び出し・フィールドの読み書き、演算子、ジェネリクスは、`SendCustomEvent` も動的確保も使いません。**

### 重くなる書き方と、軽くする書き方

- **`Func` などのデリゲートの変数を LINQ に渡す（`Select(f)`）と、デリゲートの呼び出しになります。** Send 1・Get 1・Set 2 で、実際の確保は 1 回あたり 2 回・40 B です（下の「実際の確保」の「デリゲートの呼び出し」）。これは、変数を渡した時点で、`x => デリゲートを呼ぶ(x)` というラムダに書き換えて、そのラムダをループに埋め込むためです。**ループの要素ごとに、デリゲートの呼び出しをします。** この行の数は 1 回呼んだときの数なので、要素が 100 個なら、100 回分（Send・Get・Set が各 100〜200 回）になります。ラムダかメソッド名を、LINQ の引数に直接書くと、デリゲートの呼び出しがなくなり、軽くなります。
- **デリゲートのラムダが変数をキャプチャすると、`object[]` を 3 個作ります。** 毎フレーム呼ぶところでは、引数で渡す形にすると軽くなります。
- **`List.Sort` の並べ替えの作業用の配列は、使い回しています。** `UdonSharpBehaviour` のメソッドの中では、呼ぶたびの確保はありません。普通のクラスのメソッドの中では、呼ぶたびに要素数の大きさの配列（`DataToken[]`）を 2 個作ります。
- **`List.Sort` に `Comparison` の変数を渡す（`list.Sort(cmp)`）と、比較のたびにデリゲートの呼び出しになります。** 1 回あたり Send 1・Get 1・Set 3 と、デリゲートの呼び出しと同じくらいの確保で、比較は要素数を n として n log n 回くらいあります。ラムダかメソッド名を直接書くと、デリゲートの呼び出しがなくなります。
- **`GroupBy` は、グループを外に出すと、呼ぶたびにグループごとに `object[]` と `DataList` を作ります。** グループの入れ物です。`list.GroupBy(...).Select(g => new { g.Key, N = g.Count() })` のように、グループを集計だけして、結果をグループでない値にすると、入れ物を使い回すので軽くなります。ラムダの中では、グループを `g.Key`・`g` の LINQ（`g.Count()`・`g.Sum(...)`・`g.ToList()` など）・`string.Join` の引数だけに使ってください。`OrderBy` の並べ替えの作業用の `DataList` は使い回しているので、`OrderBy` で増えるのは、`ToList()` の結果の List だけです。

## 実際の確保

### ボックス化と、ほかの UdonSharpBehaviour とのやり取り

`int`・`float`・`bool`・`Vector3` などの値の型を `object` として扱うと、ヒープに値 1 つ分の入れ物（箱）を作って値をコピーします（ボックス化）。この箱は使い終わるとすぐに不要になり、GC の対象になります。`string`・配列・`object[]`（普通のクラス・タプル・匿名型）・`DataList` などの参照の型は、`object` として扱っても同じものを指すだけなので、確保はありません。

ほかの UdonSharpBehaviour の変数を読み書きする `SetProgramVariable`・`GetProgramVariable` は、値を `object` で受け渡す形しかありません。そのため、値の型を渡すたび・受け取るたびに、1 回ずつボックス化します。

- **これは UdonSharp Plus に限らず、UdonSharp でも同じです。** UdonSharp で、ほかの UdonSharpBehaviour の引数付きのメソッドを呼ぶ（`other.Add(5)`）と、引数を 1 つずつ `SetProgramVariable` で渡し、`SendCustomEvent` で呼び、戻り値を `GetProgramVariable` で読みます。`int Add(int)` なら、1 回呼ぶたびに 2 回確保します
- `SendCustomEvent` そのものは、確保しません
- 同じ UdonSharpBehaviour の中のメソッドの呼び出しは、変数に直接コピーするので、ボックス化しません
- UdonSharp Plus のインタフェース経由の呼び出し・デリゲートの呼び出しも、相手が UdonSharpBehaviour のときは、この受け渡しをします（下の「デリゲートの呼び出し」）

### 分かっていること

- **`DataToken` を作ることは、確保になりません。** LINQ が要素ごとに `DataToken` を作っても、確保は増えません（`OrderBy(...).First()` は 0）
- **LINQ の作業用の `DataList`（`OrderBy` の並べ替え・`GroupBy` のグループの一覧）は、呼ぶたびに作らず、使い回しています。** 確保が残るのは、結果の List（`ToList()`）と、`GroupBy` のキーのボックス化、グループを外に出すときのグループごとの入れ物です
- **普通のクラス・タプル・匿名型は、値の型（`int` など）のフィールドを、作るときと書くたびにボックス化します。** 値を `object[]` に入れる作りのためです。フィールドを読むこと・メソッドを呼ぶことは、確保 0 です

### デリゲートの呼び出し

デリゲートを 1 回呼ぶと、`new` の命令は通りませんが、2 回・40 B を確保します。引数と戻り値の受け渡し（`SetProgramVariable`・`GetProgramVariable`）のボックス化です。

- コールバックの中から同じ型のデリゲートを呼んでも（入れ子の呼び出し）壊れないよう、呼び出しの補助メソッドの一部に `[RecursiveMethod]` を付けています。UdonSharp は、そのメソッドからほかのメソッドを呼ぶたびに、ローカル変数を退避用の `object[]` に積み、値の型をボックス化します。呼ぶ相手が 1 つのとき（ふつうはこれ）は、退避するのが参照だけになるように書き換えているので、この確保はありません。入れ子が深くなって退避用の `object[]` が足りなくなったときは、作り直します（`new object[]`）
- 普通のクラスの中で作ったラムダ・普通のクラスのメソッドのデリゲートは、Send・Get・Set を使わず、振り分けて直接呼びます。確保はありません（`Func<int, int>` で 0 回）
- 複数のメソッドを `+=` でつないだデリゲートは、つないだメソッドごとに Send・Set をくり返します（Get は最後のメソッドの戻り値だけ）。確保は、つないだメソッドの数によらず、呼び出し 1 回あたり 5 回・171 B でした（`Func<int, int>`。戻り値がなければ 4 回）。引数とループの番号を、入れ子の呼び出しで壊れないよう、呼び出しごとに 1 回だけ `object[]`・`int[]` にまとめる分です

毎フレーム呼ぶところでは、ラムダかメソッド名を LINQ・`List` のメソッドに直接書く（デリゲートにしない）と、デリゲートの呼び出しがなくなります。

### コルーチン

コルーチン（[コルーチン](coroutines.md)）の操作です。Send・Get・Set は使いません（待つ処理は、遅れのイベントの予約です）。実際の確保は、上と同じ測り方で、状態の表・待ち行列が足りている（同じ操作を一度動かしたあと）ときの値です。

| 操作 | new | 実際の確保 |
|---|---|---|
| 開始して、最初の `yield return` の前に終わる（引数なし） | — | — |
| 同じ（`int` の引数 2 つ） | — | 2 回・40 B（引数のボックス化） |
| `yield return null` で待つ開始 | — | —（下の「次のフレームの予約」だけ） |
| その再開 | — | — |
| `yield return` をまたぐ `int` の変数がある（`int` の引数 1 つも） | — | 2 回・40 B（引数・変数のボックス化） |
| `WaitForSeconds` で待つ開始 | — | 1 回・72 B（遅れのイベントの予約） |
| `WaitUntil` で待つ開始・条件を調べ直すフレーム | — | —（下の「次のフレームの予約」だけ） |
| 子のコルーチンを待つ開始（子が `yield return null`） | — | —（同じ） |
| **次のフレームの予約**：次のフレームを待つもの（`yield return null`・`WaitUntil`・`WaitWhile` など）が、ビヘイビアに 1 つ以上ある | — | ビヘイビアごとに 1 フレーム 1 回・72 B（待っているコルーチンの数によらない） |
| 戻り値を使う開始（`c = StartCoroutine(...)`） | — | 使わない開始と同じ |
| `StopCoroutine`・`StopCoroutine(Foo())` | — | — |
| 使い回せる状態がないときの開始（そのメソッドが同時に動いている数が、それまでより増えたとき） | `object[]`・`int[]` 各 1 | 上より 2 回・146 B 多い |

- **遅れのイベントの予約**（`SendCustomEventDelayedFrames`・`SendCustomEventDelayedSeconds`）は、Udon が予約するたびに 1 回確保します。次のフレームの予約は、ビヘイビアごとに 1 フレーム 1 回にまとめています（その代わり、ビヘイビアをまたいだ再開の順番は Unity と違うことがあります。[コルーチン](coroutines.md) の「注意」）。秒の予約は、`WaitForSeconds` で待つたびに 1 回です
- **全部の状態をなめる止め方**：`StopAllCoroutines()`・`StopCoroutine("名前")`（文字列）・`GameObject` が非アクティブになったときの停止は、そのビヘイビアが同時に動かしたことのある最大数の状態を、全部なめます（状態の表は縮まないため、動かし終わったあとも、その数のままです）。確保はありません。1 回の呼び出しの時間は、その最大数に比例します（Unity エディタの再生中に測定。1 回あたり：10 個で 約 10 µs、100 個で 約 0.1 ms、1000 個で 約 1 ms。`StopCoroutine("名前")` は約 1 割多い）。同時に動かす数が数十個までなら、問題になる大きさではありません。1 つのビヘイビアで、数百個以上を同時に動かすなら、止める呼び出しの回数に気をつけてください
- `object[]` から値の型を取り出すこと（再開したときに引数・変数を読み戻すこと）は、確保になりません。入れるほう（ボックス化）は、`int` 1 つにつき 1 回・20 B です
- 状態の表・待ち行列の配列は、足りなくなったときだけ 2 倍に広げます

### UniTask の async / await

[UniTask](unitask.md) の操作です。コルーチンに書き換えるので、上の「コルーチン」と同じ測り方（同じ操作を一度動かしたあとの値、1000 回の合計を 1 回あたりに直したもの）です。待つ側の再開は次のフレームなので、確保は「呼んだフレーム」と「再開のフレーム」に分かれます。

| 操作 | 実際の確保 |
|---|---|
| 値を返さない `async` を呼ぶ（`Foo();`）・`await Foo();`・`await UniTask.Yield();` | —（コルーチンと同じ。上の「次のフレームの予約」だけ） |
| `int v = await Zero();`（`UniTask<int>`・引数なし）・`await Zero();`（値を捨てる） | 全体で 2〜3 回・約 90 B（戻り値の置き場の `object[1]`・戻り値のボックス化） |
| `int v = await Add(1, 2);`（`UniTask<int>`・`int` の引数 2 つ） | 全体で 4 回・約 105 B（上に引数のボックス化 2 回・40 B が足される） |
| `await UniTask.WhenAll(A(), B());`（子が `Yield` を 1 回待つ） | 全体で 3 回・約 65 B（子の開始・再開を含む） |
| **待っている間の毎フレーム**：`UniTask.DelayFrame(n)`・`UniTask.Delay(...)` | 待っているものごとに 1 回・約 20 B（数え直す変数のボックス化） |
| **待っている間の毎フレーム**：`UniTask.WhenAny(A(), B())` | 待っている `WhenAny` ごとに 2 回・約 40 B（子を見張る番号のボックス化。上の `DelayFrame` などの子の分は別） |

- `UniTask<T>` の確保は、戻り値の置き場の `object[1]`・戻り値と引数のボックス化だけです（書き換え後の UASM の `new`・ボックス化と一致します）。Udon の変数のコピー（`UdonHeap.CopyHeapVariable`）は、元が `object`・`object[]` などのとき、コピー先の変数が持つ箱の型が元と違うと、リフレクションで新しい箱を作って確保します（1 回で 2 回・約 64 B）。戻り値の置き場の変数は、`new object[]` の結果（`object[]` の箱）と、キャストの結果（`object` の箱）が交互に入ると、毎回確保するので、置き場を作る補助メソッド（`__co_h`）が、キャストを通した値（`object` の箱）に揃えて返します。コルーチンの先頭で、配列のローカルを `default(T)` でなく `null` で初期化するのも、同じ理由です。1 秒に数百回以上 `UniTask<T>` を呼ぶところでは、値を返さない `async` に変えて、結果をフィールドに入れるほうが軽くなります
- 待っている間の毎フレームの確保は、待っているものの数に比例します（1000 個で、1 フレームに `DelayFrame` が約 1000 回・20 KB、`WhenAny` が約 2000 回・40 KB）。`Delay` は、予約の 1 回（約 76 B）だけです
- **秒の待ちの再開の順と、重いフレームの確保**：秒の待ち（`WaitForSeconds`・`Delay`）は、期限の順（同じ期限は開始した順）の二分ヒープで持つので、再開 1 回の命令数は待っている数の対数に比例します（#222。以前は、待っている数に比例して配列を探して詰め直していたため、1000 個を同時に待たせると、再開のフレームが約 690 ms かかり、約 5300 回・約 330 KB の確保も出ていました。今は約 37 ms で、この確保も出ません。300 個は約 80 ms → 約 20 ms）。なお、1 フレームに動かす Udon の処理が大きいと、約 5000〜5300 回・約 300〜330 KB の確保が、ときどき 1 フレームに出ます（Unity エディタの再生中に測定）。測ったのは、配列の読み書きのループを、毎フレーム k 回ずつ動かす形です（k = 1000 回が約 0.7 ms）。k が 1000 回以下（100・10・1 も）なら、3000 フレーム続けても出ません（総量は最大 300 万回）。2000 回で 1600 フレームに 1 回、3000 回で 3 回、5000 回で 7 回、7000 回で 10 回、1 万回で約 79 フレームごとに出ます。総量ではなく、1 フレームの量が決めます。1 フレームの量が同じなら、重い処理を `await UniTask.Yield()` で区切っても同じです（1 回に 100 万回を動かしても、1 万回ずつ 100 回に分けても、1 フレームが 1 万回なら出ます）。1 フレームの量を、約 1000 回（約 1 ms）以下にすれば出ません。UdonSharp Plus の機能を使わない、ふつうの UdonSharp のコード（`SendCustomEventDelayedSeconds`・`SendCustomEventDelayedFrames` で自分を呼び直して、毎回同じループを動かす）でも、同じ量・同じ間隔で出ます（1 万回で約 80 フレームごと）。原因は分かっていません（UdonSharp Plus のコードとは関係なく、Udon・エディタ側と見ています。VRChat のクライアントでは未確認）

#### GC 要因の Udon 命令の数

書き換え後の UASM（Udon のアセンブリ）を、操作ごとに調べて、GC の確保の要因になる命令を数えました。「実測」は、上の表と同じ測り方（エディタのプレイモード、1000 回の 2 回目の、1 回あたり）です。

数えた命令：

- **new**：`new object[]`・`new int[]` など（EXTERN の `__ctor__`）
- **ボックス化**：`int` などの値の型を `object[]` に入れること（待つ・再開する間に値を持ち越すためのもの）
- **イベントの予約**：`SendCustomEventDelayedFrames`・`SendCustomEventDelayedSeconds`（Udon が予約のたびに確保）
- **箱の入れ替わり**：Udon の変数コピーで、コピー先の箱の型が元と違うために確保するもの（上の説明）
- `GetProgramVariable`・`SetProgramVariable`・`SendCustomEvent`（自分自身への呼び出し）は、どの操作でも使いません（0）。型つきの null 定数からのコピーも、ありません（テストで確認しています）

| 操作 | new | ボックス化 | イベントの予約 | 実測 |
|---|---|---|---|---|
| `await UniTask.Yield()`・`NextFrame()`・`WaitUntil`・`WaitWhile` | — | — | 待つフレームごとに、ビヘイビアで共有の「次のフレームの予約」 | 待っている間の確保なし（`WaitUntil` を 1000 個待たせて、毎フレーム 0 回） |
| `await UniTask.DelayFrame(n)` | — | **待つ 1 フレームごとに 1**（数え直す変数） | 同上 | 待っている間、1 フレームごとに 1 回・約 20 B（待っているものごと） |
| `await UniTask.Delay(ミリ秒)`・`Delay(TimeSpan)` | — | — | 待つたびに `SendCustomEventDelayedSeconds` 1 回 | 予約 1 回・約 76 B。再開（`__co_sec` の実行）に、待っているものごとの確保はありません（1000 個を同時に待たせても。下の注） |
| `await UniTask.WhenAll(A(), B())`（値なし 2 つ） | — | 3（開始で 2・再開で 1） | 子の待ちごとに、次のフレームの予約 | 全体で 3 回・約 65 B |
| `await UniTask.WhenAny(A(), B())`（値なし 2 つ） | — | **どれかが終わるまで、1 フレームごとに 2**（子の番号） | 同上 | 待っている間、1 フレームごとに 2 回・約 40 B（待っている `WhenAny` ごと） |
| `UniTask<T>` を返す `async` を 1 回呼ぶ | 1（戻り値の置き場 `object[1]`） | 戻り値 1・`int` などの引数ごとに 1 | 子の待ちごと | `await Zero()` で約 87 B・2.3 回、`await Add(1, 2)` で約 104 B・4.0 回 |
| `var (a, b) = await UniTask.WhenAll(Add(1, 2), Add(3, 4))`（`UniTask<int>` 2 つ） | 置き場 2・タプル 1 | `WhenAll` 本体 3・引数 4・戻り値 2・タプル 5 | 子の待ちごと | 約 17 回・約 429 B |
| `var (i, r1, r2) = await UniTask.WhenAny(Add(1, 2), Add(3, 4))`（同上） | 置き場 2・タプル 1 | `WhenAny` 本体は 1 フレームごとに 2・引数 4・戻り値 2・タプル 7 | 子の待ちごと | 約 18 回・約 470 B（子が 1 フレームで終わるとき） |

- タプルを受ける形も、数えた命令の合計（`WhenAll` で約 17 回・`WhenAny` で約 18 回）と実測が一致します。タプルを受ける一時変数は、`yield` をまたいで持ち越さないので、`default(object[])` のまま初期化します（`new`・コンストラクタの結果と同じ `object[]` の箱のため、箱の入れ替わりがありません）。`yield` をまたいで持ち越す配列（戻り値の置き場など）は、再開のときにキャスト（`object` の箱）で戻すので、`null`（`object` の箱）で初期化します
- 実行時の補助（どの操作でも共有）にも、確保の命令があります。同時に動く数が、それまでより増えたときだけ、`new object[]`・`new int[]` が実行されます（`__co_alloc`。状態の表）。待つものが増えたとき、待ち行列の `new int[]` が実行されます（次のフレームを待つもの・秒を待つもの）。次のフレームの予約は、ビヘイビアごとに 1 フレーム 1 回です

## 読み方

- **数は、操作を 1 回実行したときに通る命令の数です。** ループの中の命令（「グループごと」）は、その数だけくり返します。エラーのときにだけ通る道は、数えていません。
- **デリゲートの呼び出しは、補助メソッドの中の Send・Get・Set も入っています。** 補助メソッドは 1 つのプログラムに 1 回だけ入りますが、呼ぶたびに、その中の Send・Get・Set は実行されます。
- **「—」は「しない」という意味です。** 普通のクラスのメソッド呼び出しやフィールドの読み書き、演算子、ジェネリクスは、`object[]` の要素の読み書きと、UdonSharp 自体のメソッド呼び出し（ジャンプ）があるだけで、Send・Get・Set も `new` もありません。
- **UdonSharpBehaviour 同士の呼び出しとの違い：** インタフェース経由の呼び出しとデリゲートの呼び出しは、UdonSharpBehaviour が相手だと `SendCustomEvent`・`GetProgramVariable`・`SetProgramVariable` を使います。UdonSharp で、別の UdonSharpBehaviour のメソッドを `SendCustomEvent` で呼ぶのと同じ重さです（普通のクラスが相手なら、型の判定とメソッド呼び出しだけで済みます）。
- `Tests/Editor/CostTests.cs` のテストは、書き換え後のコードにある命令の数（操作のたびには通らない、`+=`／`-=` の補助メソッドなどの分も含む）を固定しています。この表は、そこから操作のたびに通るものだけを数え直したものです（Redmine #169）。書き換えを変えて数が増減したときは、テストと、この表を一緒に直します。
